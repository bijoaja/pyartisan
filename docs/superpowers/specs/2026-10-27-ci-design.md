# CI — Design Spec (pyartisan)

Date: 2026-10-27
Status: Draft, awaiting approval (no implementation yet)

## 1. Background

The repo has no CI, linter, or git hook. Tests run only when someone remembers to run them, so a PR
can be merged without any check. Facts that shape the design:

- The only test today is `tests/smoke_test.py`; `2026-10-27-test-structure-design.md` moves it to
  pytest (`uv run pytest`). CI must run whichever form exists when the workflow lands.
- It has only ever been run on Windows (Python 3.14). Linux and macOS have never run it.
- `requires-python = ">=3.10"`. On Python < 3.11 the code imports `tomli` instead of `tomllib`
  (`config/__init__.py`); that dependency is declared, but Python 3.10 has never been run either.
- `pyproject.toml` has a `[build-system]` (setuptools) since PR #1. Building a wheel was checked: it
  contains `pyartisan/templates/plugin_init/` (4 files) and `entry_points.txt`, 39 files in total.
- The repo is public, default branch `main`, hosted on GitHub.

## 2. Goals

- Every PR is tested automatically on each push to the PR branch, and the result is visible on the PR.
- `main` is tested again after every merge, so a bad merge is noticed.
- The package builds, installs as a tool, and its command starts.
- Failures on Linux or macOS are found by CI instead of by a user.

## 3. Non-goals and anti-goals

Non-goals: lint or format checks, coverage thresholds, publishing to PyPI, dependency-update bots,
release automation, testing against the real `flaskiq` and `fastiq` templates.

Anti-goals (CI is wrong even if green):
- A test is skipped, marked xfail, or an OS or Python version is dropped from the matrix only to get
  green.
- The workflow needs a secret, a personal token, or network access to a private service.
- A single failing matrix cell can be merged past because the required check is unclear.

## 4. Decisions

Made by the user:
- One workflow for this repo, running on pull requests and on pushes to `main`. (flaskiq and fastiq each have their own CI spec in their own repo; this document covers pyartisan only.)
- The specs for this work live in each repo's `docs/superpowers/specs/`.

My calls (the user can overrule any of them):
- Matrix: `ubuntu-latest`, `windows-latest`, `macos-latest` x Python `3.10` and `3.14` (the lowest
  supported and the one used locally). Six cells, `fail-fast: false` so one failure does not hide the others.
- Tests run through `uv`: `uv sync --frozen` then `uv run pytest`. This depends on `uv.lock` being
  committed, which the test-structure spec decides. A lock made with `uv lock` covers the whole
  `requires-python >=3.10` range (checked: `tomli` is locked with the marker
  `python_full_version < '3.11'`, and `sqlalchemy` is locked as 2.0.55 for Python below 3.11 and
  2.1.6 above), so all six cells can use `--frozen`.
- Naming is the same in all three repos: the file is `.github/workflows/ci.yml`, the workflow `name:`
  is `ci`, and the aggregate job is `ci-ok`.
- One aggregate job named `ci-ok` that `needs` every other job and fails if any failed. Branch
  protection requires only `ci-ok`, so the required check keeps its name when the matrix changes.
- Triggers: `pull_request`, `push` on `main`, and `workflow_dispatch` for manual re-runs.
- `permissions: contents: read`, and a `concurrency` group per ref with `cancel-in-progress: true`
  so a new push to a PR cancels the older run.
- Third-party actions are pinned to a major version at implementation time (see section 8).

## 5. Jobs

| Job | Runs on | What it does |
|---|---|---|
| `test` | matrix (6 cells) | checkout, install uv, set the Python version, `uv sync --frozen`, `uv run pytest` |
| `build` | `ubuntu-latest`, Python 3.14 | `uv build`, then check the wheel contains `pyartisan/templates/plugin_init/manifest.yaml.jinja`, `.../hooks.py.jinja`, `.../README.md.jinja`, `.../LICENSE` (the plugin template's own license file, not the project license; the project license is separate at `pyartisan-<version>.dist-info/licenses/LICENSE`) and `pyartisan-<version>.dist-info/entry_points.txt` whose content defines `pyartisan = pyartisan.cli:cli` |
| `install` | `ubuntu-latest`, `windows-latest` | `uv tool install` the wheel built in `build` (download as artifact), run `pyartisan --version`, `pyartisan --help`, and `pyartisan plugin init ci-check` inside a temp dir. `plugin init` asks "Target framework?" through `click.prompt`, so the step pipes the answer (`printf 'all\n' | pyartisan plugin init ci-check`, with `shell: bash` on both OSes); no new CLI flag is needed (a pipe was used successfully by hand). Set **both** `HOME` and `USERPROFILE` to a temp dir, because `os.path.expanduser("~")` reads `USERPROFILE` on Windows and `HOME` elsewhere. After the command, assert that `<temp home>/.pyartisan/plugins/ci-check/dev` exists (symlink on Linux, junction or symlink on Windows) and that nothing was written under the runner's real home |
| `ci-ok` | `ubuntu-latest` | `needs: [test, build, install]`, `if: always()`, fails unless all three succeeded |

The `install` job exercises what pytest cannot: the installed entry point, packaged template files,
and the `uv tool` environment, which has no pip. It is the regression guard for the Windows and `uv tool`
problems already fixed (UTF-8 output, `serve` venv selection, junction fallback).

## 6. Making the check mandatory

A workflow alone does not block a merge. A failing PR can still be merged. What blocks it is a
GitHub ruleset (or branch protection rule) on `main`, which only the repo owner can set:

- Require a pull request before merging.
- Require status checks to pass, choosing `ci-ok` as the required check.
- Decide whether admins may bypass. By default an admin can; turning that off also stops the
  owner from pushing straight to `main`.

Order matters: a check name only appears in the "required" list after the workflow has run once.
So: add the workflow in a PR, let it run, merge when green, and only then create the ruleset. Claude
does not change repository settings; the owner does this step in the GitHub UI.

Pushing directly to `main` still triggers the workflow, but the result arrives after the code is
already in. Only the ruleset can prevent that.

## 7. First-run policy and risks

- The first run on Linux, macOS, and Python 3.10 will probably find failures nobody has seen. Examples
  of what to expect: tests that assume Windows paths, the junction fallback test, and the `python3`
  versus `python` behavior in the serve venv tests. A failure there is information, not a reason to
  loosen CI.
- Policy: fix real portability bugs in `src/` in a separate PR (with an issue), fix test bugs in the
  same PR as the workflow, and never skip or xfail to get green. If a failure cannot be fixed
  quickly, the matrix cell stays in the workflow, the PR stays open, and the ruleset is not enabled.
- Order of work: (1) the PR that migrates the tests to pytest and commits `uv.lock` (test-structure spec), because the matrix command `uv sync --frozen` + `uv run pytest` needs both; (2) the PR with the workflow, which triggers itself and must be green before it is merged; (3) a docs update that mentions CI in `CONTRIBUTING.md`; (4) the owner creates the ruleset. If the workflow lands before step 1, `uv run pytest` has nothing to run.
- A red cell is not merged past. If a cell fails because of a real bug in `src/`, that fix gets its own issue and PR and merges first; the workflow PR then re-runs. Borderline cases (is it a test bug or an app bug, for example the `python`/`python3` mapping in `core/engine.py` and the serve venv tests) are decided by the owner; the builder reports the evidence and asks instead of choosing.
- macOS runners are slower and billed at a higher rate on private repos; this repo is public, so the cost is only time.
- `uv.lock` pins resolved versions. If it drifts from `pyproject.toml`, `uv sync --frozen` fails. That is intended; fix by running `uv lock` and committing.

## 8. Details decided at implementation time

- Exact versions of `actions/checkout`, `astral-sh/setup-uv`, `actions/upload-artifact` and
  `actions/download-artifact`: look up the current major release with `gh api` instead of guessing.
- Exact YAML, step names, and how the wheel check is written (inline Python is fine).
- The `uv` version, pinned or latest.

## 9. Acceptance

- A PR that only touches docs triggers the workflow and `ci-ok` passes.
- A PR with a deliberately broken test makes `ci-ok` fail (try it once on a throwaway branch and close the PR).
- All six `test` cells, `build`, and both `install` cells appear in the PR checks and pass, with no skipped or xfailed test added.
- After the owner enables the ruleset, the merge button is disabled while `ci-ok` is red.
- `docs/en/CONTRIBUTING.md` and `docs/id/CONTRIBUTING.md` say CI exists, what it runs, and how to run the same commands locally.
